# 排障指南

本文档提供 POETIZE 博客系统常见问题的排查和解决方案。

## 项目部署常见问题

### 1. 项目升级时网络中断了

不用慌，可以先把这个项目删掉，部署一个新的博客项目，之后使用`poetize -restore /tmp/poetize_xxx`命令恢复数据，示例操作如下：

```bash
# 假设你当前所在的路径在 awesome-poetize-open 目录内
# 卸载旧项目
poetize -uninstall-all
# 等待卸载完成后
cd ..
# 删除旧项目
rm -rf awesome-poetize-open
# 重新部署
bash <(curl -sL install.leapya.com)
# 等待部署完成后
cd awesome-poetize-open
# 恢复数据（备份文件默认在/tmp目录下，格式为poetize_update_backup_xxx，可用 ls -dt /tmp/poetize_update_backup_* | head -1 查看最新备份）
poetize -restore /tmp/poetize_update_backup_xxx
```

### 2. 申请证书失败

**可能原因：**

1. **域名未解析到服务器**：申请证书前必须确保域名已正确解析到服务器IP。
2. **80端口被占用或未开放**：Certbot 需要使用 80 端口验证域名所有权。
3. **申请次数超限**：Let's Encrypt 有严格的频率限制：
   - **验证失败**：每域名每小时最多 5 次失败（排查问题时极易触发）
   - **重复证书**：同一组域名每周最多 5 次签发（重装系统太频繁会触发）

**解决方案：**

1. 检查域名解析是否生效（使用 `ping 你的域名`）。
2. 确保防火墙已开放 80 端口且未被其他程序占用。
3. 如果次数超限，请等待 1 小时后再试，或先使用 HTTP 模式部署。
4. 手动重新尝试申请：
   ```bash
   docker exec poetize-nginx /enable-https.sh
   ```

### 3. 部署时提示 80/443 端口被占用

**问题表现：** 启动容器时报错 `Bind for 0.0.0.0:80 failed: port is already allocated`。

**解决方案：**

1. **方法一：使用自定义端口 + CDN（推荐）**
   - 部署时直接指定端口（脚本支持自动处理）：
     ```bash
     # 交互模式输入域名时带上端口，如: example.com:8080
     # 或者使用命令行参数: ./poetize install -d example.com:8080
     ```
   - 使用 Cloudflare 等 CDN，在 SSL/TLS 设置中配置回源端口。

2. **方法二：Nginx 反向代理（适合宝塔/1Panel用户）**
   - 如果服务器已安装宝塔或 1Panel 面板：
     1. 部署时指定后端端口（避免端口冲突）：`./poetize install -d example.com:8090`
     2. 在面板中新建网站（绑定域名）。
     3. 添加**反向代理**，目标 URL 填 `http://127.0.0.1:8090`。

### 4. 升级后全站不可访问（nginx worker 持续崩溃）

**问题表现：** 升级完成、容器全部显示 `Up`，但站点打不开。CDN 侧报 `550` / `524`，浏览器报 `net::ERR_HTTP2_PROTOCOL_ERROR`。源站直连端口却是 200。

**关键特征：** nginx worker 在持续被信号杀死后由 master 重新拉起，所以容器看起来一直正常。

```bash
# 1. 确认是不是 worker 崩溃（不是容器退出）
docker exec poetize-nginx sh -c 'grep -c "exited on signal" /var/log/nginx/error.log'
dmesg -T | grep -i segfault | tail -5

# 2. 若崩溃发生在 ip2region 的 C 扩展上（Alpine musl 环境下的已知问题）
docker exec poetize-nginx sh -c 'ls -l /usr/local/openresty/lualib/xdb_searcher.so 2>/dev/null'
```

**原因：** 旧版本的镜像会把 ip2region 官方 `lua_c` 扩展（`xdb_searcher.so`）编译进镜像用于地区封禁查询。该 C 扩展在 Alpine（musl libc）+ OpenResty 1.31.x 上会高频段错误，崩在 `ld-musl` 的 `memcpy` 内部。段错误发生在 C 层，Lua 侧的 `pcall` / `xpcall` / `jit.off()` 全部无法拦截。

需要注意它并非到处都崩：1.29.2.5 上实测 25 分钟 52 万请求零 signal 11。不采用它的真实理由是另外两条：内存峰值 255.9 MB 且压测停止后不回落（纯 Lua 常驻 9 MB 量级，生产只给 128 MB），以及 p95 265.8 ms 对 28.8 ms、QPS 531.7 对 2126.4 的差距。

**解决方案：** 已在新版本中改为官方纯 Lua 实现（`docker/nginx/lua/xdb_searcher.lua`，零 C 依赖），重新执行升级即可：

```bash
bash <(curl -sL install.leapya.com) -update
```

升级后确认镜像里不再有 `.so`（返回 `No such file or directory` 才算修好）：

```bash
docker exec poetize-nginx sh -c 'ls /usr/local/openresty/lualib/xdb_searcher.so || echo "无 .so，已切换纯 Lua 实现"'
```

> 若日志里出现 `ban_check: xdb_searcher 解析到了 C 扩展`，说明用的还是旧镜像，功能与崩溃风险都退回旧状态，请重新拉取镜像。

> 若 `.so` 已不存在、worker 也不再崩溃，但站点**仍然**报 `HTTP2_PROTOCOL_ERROR`，那属于另一类问题，与 OpenResty 1.31.x 底座有关。确认当前基础镜像版本：
> ```bash
> docker exec poetize-nginx sh -c 'openresty -v'
> ```
> 若是 1.31.x，请将 `docker/nginx/Dockerfile` 两处 `FROM` 退回 `1.29.2.5-alpine` 后重新构建。已知的可复现组合是 1.31.8.1 加 brotli 动态模块：`brotli on` 时每次带 `Accept-Encoding: br` 的请求都会崩，`brotli off` 则正常，与 xdb 用 C 还是纯 Lua 无关。

### 5. 如何定位 ld-musl 段错误的具体代码位置

排查 musl 相关崩溃时最容易走错的一步，是拿 `ip` 直接减基址去查符号表。`dmesg` 里的 `[基址+长度]` 是内核记的那个 VMA 的起始地址，不是文件的偏移 0，直接减会查到完全不相干的函数。

```bash
# 1. 取崩溃现场
dmesg -T | grep -i segfault | tail -5
# segfault at 0 ip 00007f724e0a7ad4 ... in ld-musl-x86_64.so.1[7f724e098000+59000]

# 2. 把同版本的 musl 取到宿主机（容器里不需要任何工具）
docker run --rm openresty/openresty:<镜像版本>-alpine \
  cat /lib/ld-musl-x86_64.so.1 > /tmp/ld-musl.so

# 3. 看各 PT_LOAD 段的 vaddr（宿主机需有 binutils 的 readelf）
readelf -lW /tmp/ld-musl.so | grep LOAD

# 4. 真实文件偏移 = 该段 vaddr + (ip - 基址)
#    用哪一段？dmesg 里的长度与该段按页对齐后的大小一致，就是那段
#    本例 RX 段 vaddr 0x14000、覆盖 0x14000~0x6d000，长度正好 0x59000
#    0x14000 + 0xfad4 = 0x23ad4

# 5. 查这个偏移落在哪个函数。地址是定宽 16 位十六进制，字典序即数值序
readelf -sW /tmp/ld-musl.so | awk '$4=="FUNC" && $7!="UND" {print $2, $3, $8}' \
  | sort | grep "^0000000000023"
```

第 5 步只按地址前缀筛选，输出该地址段内的几个函数，形如（本例实测）：

```
0000000000023800 290  memccpy
0000000000023940 248  memchr
0000000000023a40 843  memcpy        ← 0x23ad4 落在它 +0x94
0000000000024040 238  stpncpy
0000000000024140 195  strchrnul
0000000000024240 235  strcspn
```

注意别用 `grep -B3 -A3`，那会把排序后紧邻的无关符号一起带出来（本例会把 `regexec` 印进结果，非常容易误判）。想看边界就对照 `st_value + st_size` 自己算。

想确认具体指令，反汇编那一小段（本例实测输出）：

```bash
objdump -d --start-address=0x23ad0 --stop-address=0x23ae0 /tmp/ld-musl.so
```

```
23ad4:  0f b6 06        movzbl (%rsi),%eax
23ad7:  66 0f 6e 0e     movd   (%rsi),%xmm1
23adb:  48 83 fa 02     cmp    $0x2,%rdx
```

`movzbl (%rsi)` 配合 `segfault at 0`，就是源指针为 NULL 的确定性空指针拷贝，不是野指针漂移。

**两个容易踩的坑：**

1. 偏移算错一位（比如把 `0xfad4` 看成 `0x1fad4`），加上没做第 3 步的段换算，两个错误叠加可能刚好落进另一个真实存在的函数区间，得出一个看似合理、实际完全错误的结论。
2. 用 `st_size` 判断函数归属不可靠。musl 的导出符号尺寸不一定精确，落在两个符号中间时要看前后邻居，必要时反汇编确认指令特征。

**一次真实案例的结论（2026-11-11）：**

```
dmesg:   ip 00007f724e0a7ad4  base 7f724e098000  delta 0xfad4
换算:    0x14000 + 0xfad4 = 0x23ad4
符号:    memcpy (st_value 0x23a40, size 843)，函数内 +0x94
指令:    0f b6 06  =  movzbl (%rsi), %eax
含义:    segfault at 0 + 读源指针 → 调用方给 memcpy 传了 NULL
```

**根因（2026-11-12 定稿）：**

空指针来自 in_file 类型的 buffer，不是内存 buffer 被改坏：

```c
/* ngx_http_brotli_filter_module.c:490-492 */
input_size = ngx_buf_size(ctx->in->buf);
next_input_byte = (const uint8_t *) ctx->in->buf->pos;   /* 文件 buf 时 pos 为 NULL */
```

`ngx_buf_size()` 对非内存 buf 走文件偏移分支，所以能返回一个看起来完全合法的长度：

```c
#define ngx_buf_in_memory(b) ((b)->temporary || (b)->memory || (b)->mmap)
#define ngx_buf_size(b)                                                   \
    (ngx_buf_in_memory(b) ? (off_t) ((b)->last - (b)->pos)                \
                          : ((b)->file_last - (b)->file_pos))
```

也就是说 `input_size == 0` 那道检查对文件 buf 永远不成立，NULL 直接进了 `memcpy`。gdb 断在 body filter 时实测：

```
rsi = 0x0
buf->in_file = 1   temporary = 0   memory = 0
buf->pos = NULL    file_pos = 0    file_last = 28771
r->main_filter_need_in_memory = 1    ← 标志设对了，但没起作用
```

标志为什么没起作用：copy filter 的 `need_in_memory` 只在创建 ctx 时计算一次。

```c
/* ngx_http_copy_filter_module.c:107-118 */
ctx = ngx_http_get_module_ctx(r, ngx_http_copy_filter_module);
if (ctx == NULL) {
    ...
    ctx->need_in_memory = r->main_filter_need_in_memory
                          || r->filter_need_in_memory;   /* 只此一次，之后不更新 */
```

而 `main_filter_need_in_memory` 是 filter 在 header filter 里才设的。只要 body filter 先于 header filter 被调用过一次（请求从 lua 异步 socket 回调里恢复时会这样），ctx 就以 0 建好，后续再设标志也不回头更新。

**责任判定：** 两处都有份，但该修的是 ngx_brotli。body filter 不能假设输入一定在内存里，`eilandert/coraza-nginx` 就把 file buffer 当成必须自己防御的路径（有专门的 delayed-file-buffer 测试）。同配置在 1.29.2.5 上不崩（带 br 正常返回），只是没走到这条路径。

**处置：** 锁 1.29.2.5，brotli 保持开启。1.31 这条线不再追，除非上游修了上面任一处。

顺带排除了两条假设，可以省下以后重复验证的时间：

- musl 版本差异，不成立。1.29.2.5 的 musl 1.2.5 与 1.31.8.1 的 musl 1.2.6，两版 `memcpy` 机器码逐字节相同（sha1 一致），只是排在 `.text` 里的位置不同。
- brotli 库版本差异，不成立。1.31.8.1-alpine 自带 brotli-libs 1.2.1、1.29.2.5 自带 1.2.0，而用 1.2.1 在 1.31.8.1 上压 800 多次带 br 请求零崩溃。


## 前端常见问题

### 1. npm install 依赖安装失败

```bash
# 问题：通常是网络问题导致
# 解决：配置淘宝镜像源
npm config set registry https://registry.npmmirror.com

# 然后重新安装
npm install
```

如仍失败，清除缓存重试：

**Linux/macOS:**
```bash
npm cache clean --force
rm -rf node_modules package-lock.json
npm install
```

**Windows PowerShell:**
```powershell
npm cache clean --force
Remove-Item -Recurse -Force node_modules, package-lock.json
npm install
```

### 2. 无法登录后台（点击登录无反应或报错）

**问题原因：**
生产环境（公网 IP 或域名）未开启 HTTPS，导致 **Web Crypto API** 失效，密码加密无法执行。

**解决方案：**
1. 确保服务器已启用 HTTPS（推荐使用 `poetize -update` 重新配置）。
2. 如果仅用于测试，请通过本地回环地址（`http://localhost` 或 `http://127.0.0.1`）访问。
3. 检查浏览器控制台（F12）是否有 `crypto.subtle is undefined` 错误。

### 3. 前端 docker 部署启动后 API 请求失败（跨域/404）

```bash
# 检查后端服务是否正常运行

# 确保后端服务已启动
docker ps | grep poetize-java

# 检查服务内存占用（检查后端服务或者数据库是否因资源不足导致异常）
docker stats
```

### 3. WebSocket 连接失败（聊天室无法连接）

```bash
# WebSocket 服务已集成到 Spring Boot 主程序（端口 8081），路径为 /ws/im
# 本地开发：ws://localhost:8081/ws/im
# 生产环境：通过 Nginx 代理到 wss://你的域名/ws/im

# 确保后端服务已启动（只需检查 8081 端口）
docker ps | grep poetize-java
# Linux:
netstat -tlnp | grep 8081
# macOS:
lsof -i :8081
# Windows PowerShell:
netstat -ano | findstr :8081

# 检查 Nginx WebSocket 代理配置
docker exec poetize-nginx cat /etc/nginx/conf.d/default.conf | grep -A 10 "/ws/im"
```

## Java后端常见问题

### 1. Maven 依赖下载缓慢或失败

检查 `settings.xml` 镜像源配置，已配置华为云镜像，如仍失败可尝试阿里云镜像。

清除 Maven 本地仓库重新下载：

**Linux/macOS:**
```bash
rm -rf ~/.m2/repository
mvn clean install
```

**Windows PowerShell:**
```powershell
Remove-Item -Recurse -Force $env:USERPROFILE\.m2\repository
mvn clean install
```

### 2. Spring Boot 启动失败

```bash
# 检查 JDK 版本（必须是 JDK 25，使用其他版本需修改 pom.xml 配置）
java -version
```

使用 `mvn spring-boot:run` 启动时，错误日志直接打印在控制台。常见错误及解决方案：

**1. 端口被占用**

错误：`Web server failed to start. Port 8081 was already in use`

查看占用进程：
- **Linux/macOS:** `lsof -i :8081`
- **Windows:** `netstat -ano | findstr :8081`

**2. 数据库连接失败**

错误：`Unable to acquire JDBC Connection` 或 `Access denied`

解决：检查 `application.yml` 中数据库配置，确保数据库服务已启动。

**3. Redis 连接失败**

错误：`Unable to connect to Redis`

解决：确保 Redis 服务已启动，检查密码配置。

### 3. 数据库连接密码错误

部署脚本会自动生成随机数据库密码，密码保存在 `.config/db_credentials.txt` 文件中。

```bash
# 查看数据库密码
cat .config/db_credentials.txt

# 使用正确的密码连接数据库
# 假设 ROOT 密码为 abc123xyz（实际以文件中为准）
docker exec -it poetize-mariadb mariadb -uroot -p
# 提示输入密码时，粘贴从文件中获取的 ROOT 密码

# 或使用 poetize 用户连接
docker exec -it poetize-mariadb mariadb -upoetize -p poetize
# 输入文件中的 poetize 用户密码
```

### 4. 数据库初始化失败或表不存在

```bash
# 先获取数据库密码
ROOT_PWD=$(grep "数据库ROOT密码:" .config/db_credentials.txt | cut -d':' -f2 | tr -d ' ')

# 检查是否已执行初始化脚本
docker exec -i poetize-mariadb mariadb -uroot -p${ROOT_PWD} -e "USE poetize; SHOW TABLES;"

# 重新初始化数据库
docker exec -i poetize-mariadb mariadb -uroot -p${ROOT_PWD} poetize < poetize-server/sql/poetry.sql

# 如果 RocksDB 引擎报错，使用兼容性脚本
docker exec -i poetize-mariadb mariadb -uroot -p${ROOT_PWD} poetize < poetize-server/sql/poetry_old.sql
```

### 5. 本地开发环境数据库连接失败

如果你是全新安装的 MariaDB/MySQL 和 Redis，请确保密码配置正确：

**问题表现**：启动后端时报 `Access denied` 或 `Authentication failed`

**解决方案**：

1. **检查数据库密码**：开发环境默认使用密码 `123456`
   
   ```bash
   # 测试数据库连接（mysql 或 mariadb 命令均可）
   mysql -uroot -p123456
   # 或
   mariadb -uroot -p123456
   ```

2. **如果密码不是 123456**，需要修改配置文件：
   
   编辑 `poetize-server/poetry-web/src/main/resources/application.yml`：
   ```yaml
   spring:
     datasource:
       password: 你的实际密码
   ```

3. **Redis 密码配置**：
   
   如果 Redis 设置了密码，编辑 `application.yml`：
   ```yaml
   spring:
     redis:
       password: 你的Redis密码
   ```

4. **重置 MariaDB 密码为 123456**：
   
   ```bash
   # Linux/macOS（使用 mariadb 或 mysql 命令）
   sudo mariadb -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '123456'; FLUSH PRIVILEGES;"
   
   # Windows（以管理员身份运行 CMD）
   mysql -u root -e "ALTER USER 'root'@'localhost' IDENTIFIED BY '123456'; FLUSH PRIVILEGES;"
   ```

### 1. 接口响应慢

```bash
# 检查 Redis 缓存状态
```

## 访客 IP 解析异常 / 自身 IP 被误封（全站 403）

### 症状

- 网站突然**全站 403**（或大面积 403），连正常用户的请求一并被拒；
- 后台访问统计里出现一个异常的 **IP 访问 TOP1**；
- 在 Redis 黑名单里能看到**服务器自身公网 IP**（或被拉黑的中间代理 IP）。

### 根因

访客 IP 被错误解析成“服务器自身公网 IP”，最常见于**源站反向代理指回自己的 CDN 域名形成回环**：

1. 根域名 DNS 直连源站（不走 CDN）；
2. 源站面板（如 1Panel）的站点配置写了 `proxy_pass https://www.你的域名`（指回自己的 CDN 域名）；
3. 这次回环请求由服务器自己发起，CDN 会把“发起请求的服务器公网 IP”写进 X-Forwarded-For；
4. 旧版解析取 XFF 最右端 → “访客 IP” = 服务器自身公网 IP；
5. 该 IP 被自动化拦截机制拉黑 → 所有经同一回源链路的正常请求一并 403（网站不可用），同时被计入访问统计。

新版已改为**可信链解析**：从右向左跳过 私有 / 服务器自身 / 可信代理段 地址，取第一个真实访客 IP；
封禁与统计入口也会统一排除自身 IP（双保险），即使再出现解析异常也不会全站被误封。

### 立即恢复（清理误封）

```bash
# 查看黑名单里的异常 IP（把 <自身IP> 换成你服务器的公网 IP）
docker exec -it poetize-redis redis-cli -a "$REDIS_PASSWORD" keys 'poetize:security:blacklist:*'

# 删除误封 key（同时清理攻击计数与自动化拦截缓存，避免残留）
docker exec -it poetize-redis redis-cli -a "$REDIS_PASSWORD" del \
  "poetize:security:blacklist:<自身IP>" \
  "poetize:security:attack:<自身IP>" \
  "poetize:security:automation_block:<自身IP>"
```

> 也可在后台的安全管理页对该 IP 直接点解除拉黑按钮。
> 若误封 key 未清，升级后 nginx 层也会自动**豁免**服务器自身 / 可信代理 / 私有地址的黑名单拦截，不会再因此全站 403。

访问统计中被污染的记录落在数据库 `history_info` 表（IP TOP1 即来自它），按需清理：

```sql
DELETE FROM history_info WHERE ip = '<自身IP>';
```

### 根治（升级 + 配置）

升级到包含访客 IP 可信链解析的版本后，建议在 `.env` 中补充以下配置（均可留空，留空时自动探测 / 维持默认行为）：

```ini
# 服务器自身公网 IP（逗号分隔）。不填时容器启动会自动探测一次并写入共享卷；
# 探测失败（无外网等）则跳过，仍可手动配置兜底。
SELF_PUBLIC_IPS=

# 可信代理 / CDN 回源网段（逗号分隔，可选）。填了更保险：
# 请求链中来自这些网段的地址会被跳过，不作为访客 IP。
# 回源 IP 段查询：EdgeOne 控制台的回源 IP 段页面；Cloudflare: https://www.cloudflare.com/ips/
TRUSTED_PROXY_CIDRS=

# CDN 注入的真实客户端头名（默认 X-Forwarded-For，即只用标准 XFF 链）。
# 部分 CDN 会注入专属头，可直接采用（如 EdgeOne 填 EO-Connecting-IP）。
REAL_IP_HEADER=X-Forwarded-For
```

配置后重新构建容器生效：

```bash
docker compose up -d --build nginx java-backend
```

**动态公网 IP 说明**：SELF_PUBLIC_IPS 留空时容器**启动时探测一次**（不是定时轮询）。动态 IP 变更（现已少见）后执行
`docker compose restart nginx` 重新探测即可；手动配置 SELF_PUBLIC_IPS 始终优先于自动探测。

### 排查命令

```bash
# 查看 nginx 启动时的"自身 IP"探测结果
docker logs poetize-nginx 2>&1 | grep real_ip

# 查看共享卷里的探测文件（Java 侧封禁/统计排除读取的是同一份）
docker exec poetize-nginx cat /app/runtime/self_ips

# 查看页面访问日志中的访客 IP 解析结果（xff 字段）
docker exec poetize-nginx tail -5 /var/log/nginx/page_visit.log
```

### 附：回环本身是配置错误

若根域名的入口配置（1Panel/宝塔等）把请求 `proxy_pass` 指到了自己的 CDN 域名，建议改为直连本站真实服务地址
（如 `http://127.0.0.1:<源站端口>`），或让根域名也接入 CDN，从根源消除回环。本修复保证即使存在回环也不会
再出现“自身 IP 被误封全站 403”，但消除回环后访问统计才能完全准确。
